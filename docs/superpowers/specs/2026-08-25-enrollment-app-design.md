# My Phil Enrollment App — Design Spec

Date: 2026-08-25
Status: Approved (phase 1 — enrollment funnel only)

## Context

This directory contains a design system generated by Claude from the Figma file
*"01. My Phil Component Library.fig"*: 79 React components (plain JSX, no build
tooling, inline styles driven by CSS custom properties), design tokens, and two
throwaway click-through demos in `ui_kits/` that load React via CDN `<script>`
tags and Babel-in-browser (no bundler, no routing, no real project).

The goal is to turn this into a real, navigable app — clicking a button
actually routes to another screen (browser URL changes, back/forward works) —
starting with the patient-facing enrollment funnel (Welcome → insurance →
address/payment → HIPAA/signature → thank you). The user will supply Figma
links for each screen as we go; each one gets pulled via Figma MCP
(`get_design_context` / `get_screenshot`) and built to match.

Public/shareable-link hosting is explicitly deferred to a later phase — this
spec covers getting the real app running locally via `npm run dev`.

## Goals

- A real Vite + React app, not a CDN/Babel demo.
- Every enrollment screen is a real route; browser back/forward and refresh
  behave normally.
- Reuse the existing 79-component design system as-is; extend it (not fork
  it) when a Figma screen needs something new.
- Data entered on one step (name, insurance choice, address, payment) is
  available to later steps (e.g. a review or thank-you screen) via simple
  in-memory state — no backend, no persistence across reloads.
- Keep the design-system folder as the single source of truth for
  components/tokens/assets; the app imports from it rather than duplicating.

## Non-goals (phase 1)

- My-Phil dashboard flow, MD-Dash admin tool, marketing site.
- Public link / deploy / hosting setup.
- Form validation library, real payment processing, real backend/API.
- TypeScript conversion of the component library.

## Architecture

**Stack:** Vite + React 18 + plain JSX (no TypeScript — matches the existing
component library's style; the `.d.ts` files present are documentation stubs,
not a real type-checked codebase, so introducing TS would mean typing 79
components for no prototype-level benefit).

**Location:** `app/` subfolder at the repo root, sibling to `components/`,
`tokens/`, `assets/`. The Vite app imports directly from those sibling
folders via a `@ds` alias (e.g. `@ds/components/forms/Button/Button.jsx`,
`@ds/tokens/colors.css`) — no copying files into `app/`. One source of truth;
editing a component updates it for both the design-system reference docs and
the running app.

**Routing:** `react-router-dom`, `BrowserRouter` (swap to `HashRouter` later
is a one-line change if/when we move to static single-file hosting). One
route per Figma screen under `app/src/pages/`, e.g.:

```
/welcome
/insurance
/insurance/upload
/address
/payment
/hipaa-auth
/signature
/thank-you
```

Route list grows incrementally as Figma links come in — not all screens need
to exist before the app is useful; each new screen is a new route + nav wire-up.

**State:** One `EnrollmentContext` (`app/src/state/EnrollmentContext.jsx`)
holding the fields collected across steps (name/DOB, insurance selection,
address, payment info). Provided once at the app root, consumed via a
`useEnrollment()` hook. In-memory only — resets on reload, no localStorage,
no backend calls. This is intentionally minimal: no schema validation, no
redux/zustand — a single context is enough for a linear funnel.

**Component reuse:** Pages compose existing components (`WelcomeMsg`,
`InsuranceInfo`, `AddressToggle`, `CreditCardForm`, `HippaAuth`,
`ThankyouContent`, etc.) rather than rebuilding UI. When a Figma screen
doesn't map onto an existing component, a new one is added to
`components/domain/` (or the relevant category) following the existing
conventions — inline styles off `var(--token)`, plain prop-driven function
components, no new dependencies — so it becomes reusable design-system
inventory, not page-specific one-off markup.

**Navigation wiring:** Each page component receives no `onNext`/`onBack`
props (unlike the old `ui_kits` demo pattern) — instead it uses
`useNavigate()` from react-router-dom directly, since routes are now real
paths, not array indices.

## Workflow

1. User pastes a Figma link for a screen.
2. Pull it via `get_design_context` (and `get_screenshot` for visual
   reference).
3. Build/adjust the matching page in `app/src/pages/`, adding any new
   components the screen needs.
4. Add the route and wire navigation (buttons/links) from adjacent screens.
5. User clicks through at `localhost` via `npm run dev`.
6. Repeat per screen until the funnel is complete.

## Testing

Manual click-through per screen as it's added (this is a visual/UX
prototype — no automated test suite planned for phase 1). Verify: route
renders, nav buttons move forward/back correctly, data entered earlier
appears where expected (e.g. review step), browser back/forward and refresh
don't break the flow.
